# 출시 과업 분석과 사용성 판정

RPI는 이번 작업에서 Research → Plan → Implement 순서로 적용했다. 구현 여부는 사용자가 완료할 과업과 실패 후 복구 경로로 검증한다. 합성 테스트·코드 검토·실제 기기·실사용자 조사는 서로 대신하지 않는다.

| 사용자 상황 | 완료하려는 과업 | 개선한 경로 | 검증 기준 |
|---|---|---|---|
| 바코드를 못 읽음 | 사진을 버리지 않고 쿠폰 등록 | 원본 미리보기와 직접 입력 → 필수 정보/중복 확인 → 보관 | UI에서 실제 번호 입력·저장 후 상세 원본 조회 |
| 번호가 두 개 이상 | 매장에서 쓸 번호 확정 | 후보 유지, 번호는 미확정 → 선택/직접 입력 → 원본 대조 | 자동 첫 번호 선택 금지, 중복 시 저장 실패 안내 |
| 가격/할인이 적힌 교환권 | 상품 가치 확인 | 가격·할인액을 별도 표시 | 가격이 차감 가능한 잔액으로 생성되지 않음 |
| 일부 사용한 금액권 | 현재 잔액 기록/차감 | 원금·현재 잔액 구분, 부분 차감 설정 | 수정/종류 변경으로 이미 쓴 잔액이 복원되지 않음 |
| 공유 파일 저장 실패 | 실패 여부 확인/재시도 | 확장 저장·실패 수와 실패 재시도; 앱 복구 대기열 | 파일 단위 실패가 원본을 없애지 않음; 외부 Photos 호스트 실검증은 미완료 |
| 보관 파일 이동 직후 앱 종료 | 원본 회수 | DB 참조 없는 보관 파일을 다음 실행에서 복구 목록으로 이동 | 연결된 파일 유지, 원본 bytes 유지, 반복 복구 0건 |
| 사진을 지우거나 권한 변경 | 보관한 쿠폰 계속 조회 | 등록 전에 앱 원본 사본 저장, 접근 가능한 구버전 참조도 복사 | 앱 저장소 조회 테스트. 이미 삭제된 미복사 사진 복구는 불가능 |
| 만료일을 놓침 | 미사용 쿠폰 알림 설정 | 명시적 알림 설정과 예약 개수 → 사용/날짜/삭제 시 갱신 | 실제 OS 예약 1→0과 날짜/상태/최대 50개 경계 테스트 |

## 엘렝코스 반증

- ‘바코드 검출 성공이면 쿠폰 등록 성공인가?’ 일반 상품/회원 번호와 혼재할 수 있다. 검출과 확인 승인을 분리했다. 다중 번호는 사용자 선택 전 사용 번호로 확정하지 않는다.
- ‘사용자가 대충 사용법을 아니까 오류 설명도 필요 없는가?’ 기능 설명은 줄였지만 실패 이유와 다음 행동은 남겼다. 숨겨진 폼 아래 오류 대신 시스템 경고, 확인 승인 버튼은 화면 아래에 고정했다.
- ‘테스트의 예약 개수만 맞으면 알림 취소가 검증됐는가?’ 처음에는 무조건 중앙 탭이 Settings를 열었다. 실패 캡처로 반박하고 권한 창 버튼만 처리해 재검증했다. OS 실제 전달 시각까지 확인한 것은 아니다.
- ‘원본 파일이 있으면 언제든 복구할 수 있는가?’ DB 참조 없이 Saved에 남으면 화면에서 못 찾는다. 다음 실행 복구와 등록 원본 보호를 추가 검증했다.
- ‘Archive가 성공하면 심사 직전인가?’ App Store 프로파일 export가 실제로 실패했다. 개발 빌드와 배포 Validate, 정책/지원 공개, 기기 QA를 따로 gate로 남겼다.

## 브랜드와 반복 사용

온보딩·아이콘·강조색에 겹친 선물 티켓을 일관되게 사용한다. 정렬된 보관함, 원본 확대, 실패 항목 복구, 선택한 만료 알림은 다시 앱을 찾을 이유를 제공한다. 브랜드 기억과 재방문율은 관찰 데이터가 없으므로 ‘좋다/높다’고 확정하지 않는다. 출시 전 실제 사용자에게 등록→확인→매장 제시→사용 기록 과업을 관찰하고 잘못된 번호 선택/되돌아감/문의 원인을 기록한다.
